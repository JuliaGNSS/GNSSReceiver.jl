Acquisition & Tracking Parameters

Almost everything about how the receiver behaves is controlled through keyword arguments to receive (and, for the live path, gnss_receiver_gui). This page groups those keywords by pipeline stage and shows how to set them. The full, authoritative list lives in the receive docstring at the bottom of the page.

Systems: multi-constellation and multi-band

receive's second argument selects which signals to receive:

  • A single system — one GNSS signal (GPSL1CA()), a CombinedSignal pilot+data pair, or a tuple of these — that shares one RF band:

    receive(measurement_channel, GPSL1CA(), sampling_freq)

  • A tuple of systems sharing one RF band, fused into a single multi-GNSS PVT solution. GPS L1 C/A and Galileo E1 both live on L1, so they can share one stream:

    receive(measurement_channel, (GPSL1CA(), GalileoE1B()), sampling_freq)

    (All systems in the tuple must share one RF band; mixing bands — e.g. L1 and L5 — throws.)

    Galileo E1B needs a high sampling frequency — or its BOC(1,1) approximation

    GalileoE1B() is the full CBOC(6,1,1/11) signal, whose BOC(6,1) component requires a sampling frequency above ~12.3 MHz (Nyquist for the 6.138 MHz subcarrier). At typical low SDR rates — like the 2.048 MHz used in the examples on these pages — use GalileoE1B_BOC11() instead, the BOC(1,1) approximation that ignores the BOC(6,1) component and correlates fine at low rates (at a small C/N₀ penalty).

  • For several RF bands, use the multi-band method: a tuple of measurement channels (one per band), a tuple of per-band system groups and a tuple of interm_freqs, all aligned band-by-band. Every band is fused into one solution with per-constellation clock biases and per-band inter-frequency biases:

    receive(
    (l1_channel, l5_channel),
    ((GPSL1CA(),), (CombinedSignal(GPSL5Q(), GPSL5I()),)),
    sampling_freq;
    interm_freqs = (0.0u"Hz", 0.0u"Hz"),
)

A CombinedSignal(pilot, data) tracks the dataless pilot (which the loops range on) and the data component (whose navigation message is decoded) together in one group.

Acquisition

Acquisition is the search that finds which satellites are visible and gives a first estimate of their code phase and Doppler. It re-runs at most every acquire_every of signal time. Its coherent integration length and Doppler resolution are no longer user knobs — they are derived internally, per system, from the tracking loop's carrier-Doppler pull-in range, so that the worst-case post-acquisition residual always lands inside the loop's capture range. A detection is accepted purely on a CFAR test (constant false-alarm rate) at a fixed internal false-alarm probability — there is no acquisition CN0 threshold.

KeywordDefaultMeaning
acquire_every10u"s"How often (in signal time) acquisition re-runs to look for new satellites.
prnsnothingWhich PRNs to search for. nothing ⇒ each constellation's default range; a per-GNSS NamedTuple/Dict keyed by constellation; or a plain collection applied to every system.

Restricting the PRN search

prns narrows (or widens) the satellites acquisition searches for. For a multi-GNSS run you can give a per-constellation list keyed by constellation name:

data_channel = receive(
    measurement_channel, (GPSL1CA(), GalileoE1B()), sampling_freq;
    prns = (GPS = [1, 8, 30], Galileo = [3, 9, 24]),
)

A plain collection is applied to every system, and nothing uses each constellation's default range. Each system's search is further restricted to the PRNs that actually broadcast its signal.

Lock detection

A satellite is tracked only while it is in lock. Lock is declared per satellite by a CodeLockDetector — a threshold on the post-integration SNR — and a CarrierLockDetector — the narrowband difference/power phase-lock indicator Σ(I²−Q²)/Σ(I²+Q²). Both track elapsed signal time, so their behaviour is independent of how the signal is chunked.

The lock knob surfaced directly on receive is the code-lock CN0 threshold:

KeywordDefaultMeaning
code_lock_cn0_thresholdnothing (⇒ 30u"dBHz" per signal)A satellite is declared code-locked while its estimated CN0 stays above this, referred to a one-code-block record.
data_channel = receive(
    measurement_channel, GPSL1CA(), 2.048e6u"Hz";
    code_lock_cn0_threshold = 32u"dBHz",   # stricter lock
)

The threshold is referred to a record spanning one primary code period, because what decides detectability is the post-integration SNR CN0 · T rather than CN0 on its own. When tracking integrates over N code blocks per record, a satellite therefore holds lock at 10·log10(N) dB less CN0 — 3 dB at two blocks — since the longer coherent integration recovers exactly that much. Anchoring to the code period rather than to the symbol period keeps the number meaning the same thing for the default one-block cadence and stays defined for pilot signals, which have no data rate.

Two stages: handover, then steady state

The acquisition → tracking handover is deliberately coarse — the acquisition Doppler bin is half the tracking loop's pull-in range, and the code phase is only resolved to the sample grid. Until the loops have pulled those errors in, the prompt correlator sits off the correlation peak and reports less power than the satellite really has, so a perfectly healthy satellite looks weak. A 0.25-chip code-phase error costs 2.5 dB of prompt amplitude on BPSK (GPS L1 C/A, autocorrelation 1 − |Δτ|) but about 12 dB on BOC(1,1) (GPS L1C, 1 − 3|Δτ|), whose correlation peak is three times narrower — and BOC signals also have the slowest code loops, so they hold that deficit longest.

Both detectors therefore run a pull-in stage with a generous out-of-lock allowance, latching into a tighter steady state once the satellite has either strung together enough good evidence to be considered converged or exhausted its pull-in window. This buys handover tolerance without making a genuine signal loss slower to notice.

Ranging is gated separately from tracking, and on a later criterion. A satellite in its pull-in stage is still kept — that is the point — but it does not contribute to the PVT solution until its loops have settled, because a code phase that is still converging produces a pseudorange biased by metres to tens of metres. time_in_lock_before_calculating_pvt alone would not achieve this: it counts from the handover, so it can elapse while the loops are still settling.

That stage is observable rather than hidden: each satellite's SatelliteDataOfInterest carries is_ranging_ready, and the dashboard's CN0 panel draws a still-settling satellite yellow rather than green (see Graphical User Interface). Without that, a satellite held through the handover is indistinguishable on screen from one the PVT solve is ignoring for no reason.

Those two are deliberately separate thresholds rather than one, because they pull in opposite directions. Tightening the dwell wants to happen early, so that a fade after a successful handover is noticed on the steady-state timescale. Admitting a satellite to ranging wants to happen late, because C/N0 recovers long before the code loop does — on BPSK the prompt only loses 1 − |Δτ|, so a GPS L1 C/A satellite looks healthy almost immediately while its DLL is still tens of metres out. Measured: at 200 code periods of clean evidence the residual code phase is 0.09-0.19 chip (26-54 m); at 600 it is 0.007-0.09 chip (2-27 m). Using one threshold for both meant either admitting the 54 m bias or tripling the fade-detection delay.

Ranging readiness needs a timer as well as an evidence path, for the same reason the pull-in stage does: the evidence clock is reset by any out-of-lock verdict, so an uninterrupted run is a bar a satellite can fail to clear indefinitely. That is not hypothetical — at the default 30 dBHz threshold MomentsCN0Estimator calls a healthy record out of lock often enough that the run is rare (measured per-4 ms-chunk rates of 0.42 at 30 dBHz, 0.23 at 31, 0.095 at 32), and against any disturbance recurring on a period shorter than the run the evidence path never fires at all while the dwell sits comfortably in lock. The satellite would then be tracked, converged, and silently absent from the PVT solve forever; since PVT needs four satellites, that trades a degraded fix for no fix. The backstop admits such a satellite once enough signal has elapsed — two code-loop time constants — with its out-of-lock clock still inside what steady state tolerates. What it concedes is a few metres of extra code-phase thermal jitter (1σ of 0.039 chip, 11 m, at 30 dBHz against 0.004 chip, 1.2 m, at 45), not a converging handover bias, which is inside the band the evidence path already accepts.

One residual case is left open deliberately: a satellite whose accumulated out-of-lock time parks between the steady-state and pull-in allowances — 200 to 600 code periods — never leaves the pull-in stage, and so never becomes ranging-ready either. Reaching it takes a burst of failures followed by a sustained near-50% duty cycle; under a stochastic signal the clock random-walks out of that band, either down to zero (whereupon it latches) or up past the pull-in allowance (whereupon lock is lost and the satellite is reacquired). Closing it would mean letting the pull-in stage latch while its clock is still above the steady-state threshold, which is exactly the discontinuity the latch guard exists to prevent.

Timings scale with the code period

Every detector timing is configured as a multiple of the ranging signal's primary code period rather than in seconds, because that is what the tracking loops' time constants scale with: Tracking sizes its default bandwidths at B_L·T ≈ 0.018, so a 1 ms code gets an 18 Hz carrier / 1 Hz code loop while a 10 ms code gets 1.8 Hz / 0.1 Hz.

GPS L1 C/A1 ms80 ms200 ms600 ms680 ms2 s
Galileo E1B4 ms320 ms800 ms2.4 s2.7 s8 s
GPS L1C-D10 ms800 ms2 s6 s6.8 s20 s

"Ranging ready" is the evidence path — what a healthy satellite achieves; "ranging backstop" is the timer that bounds the wait for one whose evidence never comes cleanly.

A dwell fixed in seconds means something different on every signal: the 200 ms this receiver used to allow is 200 code periods on GPS L1 C/A but only 20 on GPS L1C-D, against loops that are ten times slower — which is why lock detection failed on the slower signals while GPS L1 C/A looked fine. The GPS L1 C/A numbers are unchanged.

One consequence worth stating outright: on codes longer than 1 ms these timings, not time_in_lock_before_calculating_pvt, are what actually decide when a satellite joins the solve. A healthy GPS L1 C/A satellite is ranging-ready at 680 ms, well inside the 2 s default, so that knob still binds there. On Galileo E1B (2.7 s) and GPS L1C-D (6.8 s) it no longer does, and raising it below those figures has no effect at all. The extra seconds are in practice dwarfed by the tens of seconds of subframe decoding that set time to first fix.

The remaining detector settings — the stage timings in code periods, the carrier phase-lock threshold and its smoothing window — are set at detector construction; see the LockDwell, CodeLockDetector and CarrierLockDetector docstrings in the API Reference for the defaults and the measurements behind them.

data_channel = receive(

    pvt_update_interval = 200u"ms",
    enable_tropospheric_correction = false,

)

Custom per-chunk output

extract replaces the per-chunk payload builder; the default default_data_of_interest emits a ReceiverDataOfInterest. Pass your own extract(receiver_state) to emit anything else — see Custom Receiver Output.

Multi-antenna processing

For multiple antennas (NumAnts(N) with N > 1) the post-correlation filter is an EigenBeamformer. The number of antenna channels in each measurement channel must equal N in num_ants.
